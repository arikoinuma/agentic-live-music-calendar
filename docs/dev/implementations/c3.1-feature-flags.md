## Context

### What this milestone is

Today a behavior that must differ by environment, or be switched off without a code change, is a loose variable or a promise in a plan: production's cron "left off until C11", the model per environment, the non-production gate. C3.1 gives those **one small mechanism**: a registry of named toggles, one function to read a toggle, and one variable per environment that sets it. It is deliberately not a flag service (Dep-D17): no database table, no Vercel Flags, no vendor, no percentage rollouts, and a change takes a restart.

It ships one real flag, `worker.scheduled_runs`, and the gate that uses it: a worker started with `--trigger scheduled` exits quietly when the flag is off. That gate is what makes it safe to create a Railway cron service at all (C8-D4), which is why C8 waits on this milestone.

The word is **feature flag** for these toggles. "Flag" alone stays the user flagging a wrong listing (`arch-initial.md` §7), and the code already has a `RunTrigger.FLAG_THRESHOLD` that means the latter.

### What C3.1 delivers

1. **`app/flags.py`** (Python, the only registry): a frozen `Flag` record, the `FLAGS` table, `is_enabled(name, *, metro=None)`, `effective_flags()`, and `environment_problems(environ)`, which `Settings` calls at startup so an unregistered or malformed `FLAG_*` variable stops the process (C3.1-D12).
2. **The first flag**, `worker.scheduled_runs`, default off in every environment, and **the gate** in the worker's `main()` (C3.1-D1, C3.1-D13, C3.1-D14).
3. **A record on every run**: `agent_run.feature_flags` (JSONB, nullable, expand-only), written from a snapshot the entry point takes at start (C3.1-D3, C3.1-D15).
4. **Visibility**: `/health` lists the effective values outside production (C3.1-D16), and the frontend's status page shows them.
5. **The TypeScript half** (C3.1-D2): the registry generated from the Python one by `make types`, and a server-only `isEnabled(name, { metro })` with no caller yet, tested against the same table of cases as Python.
6. **Hygiene** (C3.1-D18): `make flags` lists every flag with owner, creation date and removal condition; tests fail when code reads an unregistered flag, when a flag is registered and nothing reads it, or when `environments.md` drifts from the registry.
7. **Documentation**: a "Feature flags" section in `environments.md` (how to add, read, set and remove one), the `C3.1` scope and the term in `conventions.md`, and the corrections to the neighboring documents (Step 9).

## Risks and traps

| Risk | Why it matters | How the plan handles it |
|---|---|---|
| `Settings` importing `app.flags` closes a cycle if the flags module ever reads settings | the API, worker and Alembic would fail at import, before any test names the cause | D6: `app/flags.py` imports nothing from `app.config` and reads `os.environ` directly; a test imports it with `app.config` blocked |

| A shell or CI variable that happens to start `FLAG_` stops every process | the startup rule is strict by design | the message names the variable; ordinary tools do not use the prefix. If one ever does, the answer is a rename of ours, not a looser check |
| The gate silently stops mattering | a deploy that sets `--trigger manual` in a start command would ignore the flag | C8-D4 makes the image's command `--trigger scheduled`; D13 narrows `--trigger` to `scheduled` and `manual`, and T11 pins that the other two `RunTrigger` values are refused, so `manual` is the only ungated trigger |
