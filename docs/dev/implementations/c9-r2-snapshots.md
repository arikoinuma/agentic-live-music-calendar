## Context

`audit_log.snapshot_key` has existed since A1 and has always been NULL. `fetch_node` fetches a venue's page, keeps the decoded HTML in `state.page_html`, and the audit row it leaves records only the URL, the date, an error and `text_chars`. The page itself is kept nowhere: the extract row's MongoDB staging document holds what the model was sent (`sent_text`), and the structured (JSON-LD or embedded-events) route sends the model almost nothing, so for a show read in code the raw markup is gone the moment the process exits. C9 closes that: after a successful fetch the worker writes the page to a Cloudflare R2 bucket, and the fetch row carries the object's key (and a hash of what was stored), so a person can go from a row in the calendar to its `audit_log` rows to the page those rows came from. Definition of done point 5 needs it, and C11's burn-in needs stored pages to label (`alpha-deployment-plan.md` C11, "Burn-in").

It is a small milestone: one new module, one new field on the worker's context, one write in `trace.audited`, four settings, and an account setup that is Ari's. **The pipeline's behaviour does not change except that a fetch now also writes an object, and (D1) a fetch that cannot be stored stops that venue's run.**

(a) The run stops with no fetch row (the reason only in the log). (b) The run goes on, `snapshot_key` stays NULL and the error is written into the fetch row's `detail`. | **(a′), accepted by Ari on November 19, 2026 as the floor, not the final policy.** `S3SnapshotStore.put` raises `SnapshotError` (K2); `trace.audited` catches it, appends the fetch row with a NULL key and `detail.snapshot_error`, and then re-raises, so the run stops and no commit happens for that venue that day. ### Decisions made in the plan (recommendations; reviewer, please challenge)

| ID | Decision | Reason |
|---|---|---|
| **D4** | **What is stored: `state.page_html`, UTF-8 encoded, as `text/html; charset=utf-8`.** Not the raw wire bytes. The fetch row's `detail` gains `snapshot: {"bytes": n, "sha256": "<hex>"}` (the length and SHA-256 of exactly the bytes uploaded), the object also carries the hash as user metadata, and `snapshot_key` carries the key. Nothing is stored when the fetch failed (`fetch_error` is set; `fetch_node` assigns `page_html` *before* it raises `EmptyPageError`, so `page_html` alone is not the test) or when `page_html` is `None` (an image file). With a real store and `state.run_id` `None` the put raises `ValueError` (a bug, not a venue's failure; `NoSnapshotStore` ignores the run id, so a hand-built test state is unaffected). | `fetch_html` returns `response.text`; the wire bytes are not kept, and keeping them would change `fetch_html`, which the eval's capture shares. `page_html` is what the extractor and validator read and what a captured fixture holds, so a snapshot can be dropped into `captured_pages/` and replayed. The hash is what makes "resolves to the page it fetched" checkable without trusting the filename: re-hash the downloaded object and compare. **Accepted loss:** httpx's charset guess can differ from the page's own bytes for an oddly encoded page; the snapshot is "what the pipeline saw", which is the audit question. |

### The ordering trap: deploying C9 before the variables

The staging cron worker runs daily and, with the flag off, logs a skip. **With C9's code and no `R2_*` variables, D8's pre-gate check makes that skip exit 2.** Railway deploys `main` on merge. So: **Step 6 (the bucket, the token, the variables) before the merge.** Setting `R2_*` variables early is harmless: `Settings` ignores process variables it has no field for, so today's code does not notice them. - *Key point of interest:* the key is built only from which venue, which date and which run, never from the page's content. ## Deferred: decided to come back to, and what reopens each

Written from Ari's discussion of D1 on November 19, 2026. **Nothing here is built in C9.** Elsewhere these are `C9-DF1` to `C9-DF4`.

**What D1 already gives**, which is why these can wait:
- botocore's standard mode makes up to four attempts with backoff inside one call (about 100 s worst case, D7), so a network blip is already retried.
- A failure that survives that costs **one venue one day**: the failure happens before extraction, so no model cost is wasted, and the calendar is stale, not wrong.
- The next daily run refetches, and `VENUE=<n> make worker` re-runs one venue by hand.
- A permanent failure (a revoked token, a wrong bucket) is caught by the startup preflight before venue 1 (D8); mid-run, 401, 403 and 404 are not retried by botocore, so each venue fails fast.
- D14 records the kind of every failure, so the data these items need is already in the audit trail.

| ID | Item | Why it can wait | What reopens it | Notes for whoever builds it |
|---|---|---|---|---|
| **DF1** | **An end-of-run retry pass for transient failures.** After the other venues finish, `run_all` re-runs each venue that failed with `kind == "transient"` once, minutes after the blip. | The day-level retry exists, and a miss costs one venue one day. | A transient `snapshot_error` on more than one day in the first week of C11's burn-in (count fetch rows by `detail -> 'snapshot_error' ->> 'kind'`). | **Refetch, do not re-put**, so every fetch row stays one real fetch and its `fetched_on` stays true; it is a new run for that venue. `auth` and `config` are never retried: permanent, so a retry only wastes time. |
| **DF2** | **A circuit breaker.** After N consecutive transient failures in one run, stop the remaining venues. | It saves only time and fetch load on venue sites: a hard R2 outage costs about 100 s per venue (about 20 minutes for twelve), and no model cost is spent because extraction never starts. | The venue count growing well past a dozen, or a run's wall-clock starting to matter. | Count consecutive `transient` kinds only; an `auth` failure on one venue already predicts the rest, so it could trip the breaker at once. |
| **DF3** | **A staging outbox.** When R2 refuses a page, stage it in MongoDB (already the A4 sink) and upload it later, so commit proceeds once the page is durable somewhere. | It is the only option that keeps a day of data through a long outage, and it costs a second sink, a reconciler, Atlas's free-tier size (`c1-env-revalidation.md`), and a state where a fetch row's key is pending. A4-D3's principle is "evidence durable before the transaction", not "evidence in R2". | R2 outages repeatedly costing more than one stale day, or a missed day ever mattering to a visitor. | The row would need a "pending" state that `fetches_without_snapshots` does not flag and a later pass that fills the key. |
| **DF4** | **A retention rule.** Today every snapshot is kept forever (D10, a stated position). | About 3.7 GB a year worst case for twelve venues against a free 10 GB, and going over is cents (U5). | C11's burn-in projecting more than half of 10 GB a year, or the venue count growing, or storage cost appearing. | See the list below. |

**What a retention rule would have to respect (DF4):**
- **Keep the hash.** `detail.snapshot.sha256` and `bytes` stay in Postgres forever, so a row proves what was fetched after its body is gone.
- **An expired object must read differently from a failed write.** `snapshot_key` is recomputable from the row (K1), so an existence check or an explicit "expired" marker tells them apart; decide which when a rule exists. `fetches_without_snapshots` only looks for NULL keys and would not flag an expired one.
- **Staging and dev first.** Nothing depends on their evidence. A lifecycle rule is a dashboard setting with no code, and **Ari sets it, not the worker**: the worker's token cannot manage lifecycles (the read row in Context).
- **Production longer, and longest for fetches that changed the calendar.** A prefix rule cannot see that; it would need a job reading the commit rows.
- **Deduplicating unchanged pages by hash is the biggest saver and the costliest change**: venue pages are mostly unchanged day to day, but it breaks "one key per fetch row" (D5) and needs deletion that knows which rows still point at an object. **Measure the saving before deciding**, from the audit table alone: distinct `detail.snapshot.sha256` per venue over its fetch rows.
- **Infrequent Access is not worth it**: $0.01 against $0.015 per GB-month, a 30-day minimum and a retrieval fee.
