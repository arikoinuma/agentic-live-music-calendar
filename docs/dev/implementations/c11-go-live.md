### The five traps this order exists to avoid

1. **The guard before the variable (C10-D1, C10-D13).** The new API refuses to start without `API_SHARED_SECRET`, and a new frontend with no secret is refused by it. Both variables exist **before** the promotion.
2. **The proof of the guard cannot come before the promotion.** C11's first bullet in the deployment plan says to create the pair and "then confirm an unauthenticated call to production's API is refused". Today's production API is the **old, unguarded code**, so that call answers 200. The proof is only meaningful **after** the promotion (D7).
3. **A migration that changes a populated table, never rehearsed.** The promotion runs `c4a1e5b7d903` (`metro slug`) and `d7b3c2a91e45` on live data in the API's pre-deploy. The rehearsal on a Neon copy comes first and is a hard gate (D6, Step 3).
4. **The public site changes the moment the branch moves.** `www.pebblebeats.com` is public already (an empty calendar since November 2), with no gate and no `noindex`. After the promotion it serves the **new** build, with whatever the database holds then. The promotion's own new risks are the error window and a rollback that does not work as assumed (D8), and the answer to the empty calendar is to populate soon after, not to rush the promotion (D2).
5. **`SITE_ZONE` before `msp` is attached.** With `SITE_ZONE=pebblebeats.com`, `www` becomes a reserved slug and redirects to `msp.pebblebeats.com`, which is not attached until the last step (`environments.md`, "Hosts, the gate and `noindex`"). The domain goes on first, the zone second (D6, Step 9).

One more fact belongs here: a worker's first hosted run needs all four `R2_*` variables even when it only skips (C9), so the production bucket and token are created in Step 2, before the production worker's skip proof (Step 5).

## Test approach

There is no code, so **no unit tests**; the "check first" discipline of the build plan (§3) is applied to the runbook itself: **each step below carries its proof (what you will see if it worked and what it means if you see something else) before the step is run**, and the proof is written so it can fail. The two code items (D1) have their own tests-first records. The repository's `make check` and `make designation-check` run on this branch for the docs it touches (Step 13) and nothing else.
