## Context

A2.1 ended at **56 of 60** shows correct on the gated pages (White Squirrel ×2, 7th St Entry, Mortimer's) against a standard of 100% for dates and acts (`A2.1-D1`). The four misses are act-naming slips by the ~4B-parameter local model, and A2.1 named a larger model for the act splitter as the next fix (`A2.1-E1`). A larger model doesn't fit the development laptop, so this milestone moves inference to DeepInfra (the production provider, `arch-initial.md` §5/§7) and tries to close the gate there.

Two further facts shape the plan:

- **The gated pages are no longer held out.** The prompt's conventions were drawn from them and tuned against them (`A2.1-CR2-2`; the prompt's examples have since been invented, `test_no_prompt_quotes_a_labelled_answer`, but the tuning remains). A pass on them alone is not an accuracy claim about venues the pipeline has not seen. The milestone's second gate is a fresh, held-out capture.
- **Four kinds of model call, not one.** On the adopted configuration a page makes up to four distinct kinds of call: the page model (JSON-LD route: none; model route: listings), the act splitter (both routes), the status question, and reconcile's ambiguous-artist question (`artist_match.ask`). All four are handed the same `instructor_client` and, today, the same `RequestOptions` (`extraction.PIPELINE_OPTIONS`, `nodes.py:164,169,291`). The retry policy's escalation swaps the model name on *all* of a page's calls (`policy.plan_for_attempt`, `replace(base_options, model=model)`). Making "the splitter alone" a bigger model therefore needs a seam that does not exist yet.

## Test approach

Tests come first (`alpha-build-plan.md` §3). Nothing here may call DeepInfra or Ollama in CI: the cloud and CI runs have neither (`AGENTS.md`, "Cloud sessions"), so the model is `tests/fakes.py`'s `scripted_client()`. Expected values come from the specs named in each row, not from the code under test.

**1. Configuration (`agent_worker/tests/test_llm_config.py`, new; pure).** `Proves:` rows, each driven by a table of settings → resolved roles:
- With no new variables set, every role resolves to **exactly today's** options (`model=settings.model_name`, `temperature=0.0`, provider `ollama`) and `request_kwargs` for them is byte-identical to the pre-C6 dict (the A2.1 56/60 result stays valid, as `test_retry_plumbing`'s first-attempt test pins for the request).
- A role with its own model name uses it; a role without one falls back to the page model; the escalation model replaces the model on every role (today's behaviour, preserved on purpose; D4).
- Provider `openai_compatible` omits `extra_body`; provider `ollama` sends it (the decision in D5, from Step 1's measurement).
- An empty-string model name ("`SPLITTER_MODEL_NAME=`", the shape `A3-CR1-3` already hit for `ESCALATION_MODEL_NAME`) means "not configured", not a model named "".
- **The endpoint rule is a worker start-up check, not a `Settings` validator** (`C6-PR1-1`). `Settings()` is built by every entry point including the hosted API, which never calls the model and sets no `MODEL_BASE_URL`; a `Settings`-level "hosted + `localhost`" rule would refuse the API at its first deploy. A pure function `model_endpoint_problem(app_env, provider, base_url, api_key)` sits beside the worker's existing `MONGODB_URI` refusal (`agent_worker/main.py`) and is table-tested: for any `app_env` other than `local`, a base URL host of `localhost`/`127.0.0.1`/`::1` is refused ("`localhost:11434` doesn't exist on Railway", `env-setup.md` Phase 8), and so is `openai_compatible` paired with the placeholder key `"ollama"` (it would otherwise fail with a 401 on the first call). `local` with a hosted URL is allowed: the laptop is where C6 runs. The API's `Settings` gets no such rule, and a test asserts the API's settings build with the new fields at their defaults under `APP_ENV=prod`.

**2. Threading (`test_extraction.py`, `test_act_split.py`, `test_retry_plumbing.py`, `test_graph*.py`).** `Proves:` that the splitter and status calls receive *their own* options and that the page call does not receive the splitter's: a scripted client records `model` per call and the test asserts the sequence. Also: the status pass's second splitter call (the `split_titles` lambda for listings the status merge adds, `extraction.py:231`) receives the *splitter's* options, not the page's; tier 3 swaps the model on the page, splitter and status roles; and the matcher's options come from its own role and are **not** changed by escalation (`C6-PR1-2`). The existing first-attempt-byte-identical test stays green.

**3. Eval harness (`test_eval_harness.py`).**
- The harness's client is built from the same settings as the pipeline's (one factory, `llm.build_clients(settings)`); a test builds both and compares `base_url` and model.
- Under a hosted provider, `model_provenance` makes **no request to `localhost:11434`** (monkeypatched `httpx.get` that fails the test) and records provider, base-URL host, requested model id and the response's own model/fingerprint fields where present.
- Token usage on a fake completion with a `usage` block lands in the run record, summed over every call in the run (page, splitter, status), and a completion without `usage` records `None`, never 0.
- `--model`, `--splitter-model`, `--status-model` overrides change only the role they name, and are recorded in the results file's `request_options` (the A2.1 rule that a results file reproduces its run).
- The results file records the sha of `labels.py` at run time, so a held-out score can be shown to postdate its labels (D8).

**4. Held-out labels (`test_labels.py`).** C5's plan (`c5-pipeline-eval-harness.md`, C5-D3; on branch `origin/claude/sharp-turing-guqvvh` until merged) already defines the mechanism, and C6 **adopts its names and semantics** instead of a parallel scheme (`C6-PR1-5`): `PageLabel.held_out`, `held_out_fixtures()`, `--set held_out`, held-out pages excluded from `gated_fixtures()` and from the default sets, and `labels_sha` in the results file. If that plan changes, C6 follows it. `Proves:` that a held-out label has a fixture name in `PAGE_LABELS`, carries a `source_line` per show, is not in `gated_fixtures()`, and that `--set gated` still selects exactly the four A2.1 pages (so old results stay comparable). `test_no_prompt_quotes_a_labelled_answer` (in `test_prompts.py`) already iterates every page in `PAGE_LABELS`, so held-out labels are covered once added: no change, but a test asserts a held-out page is in the iterated set. C5's harness imports `run_eval.model_provenance` and the pipeline client, so Part 1's `llm.py` and `run_eval.py` changes ripple into C5; C5 says hosted provenance is C6's to add, so the two plans meet there and the later merger rebases.

**5. `_on_page` (`test_status_check.py`).** Tests first: the existing test that pins the substring behaviour is rewritten to pin whole-word matching: "mo" is *not* on a page whose only match is "more", "month" or "Armory"; "U2" and "MO" as whole tokens are on the page. The existing rows for the identifying-word path stay as they are.

**6. Not testable in CI, and said plainly.** Everything that calls DeepInfra: the probe, the parity run, the rungs, the held-out scoring, the 5-run confirmation, throughput and cost. These run on Ari's laptop (the key lives in `apps/api/.env` as `MODEL_API_KEY` only, gitignored and inert while the provider is `ollama`; the base URL, provider and model are passed as a one-command override, the pattern `environments.md` uses for databases, so `make worker` on the laptop never silently becomes a hosted run) and are recorded in this file's Implementation log with the exact commands. A cloud session cannot do them, and says so in the PR (`AGENTS.md`, "Cloud sessions"). The 14 real-page tests skip in the cloud as before.

### Part 2 — the accuracy work (waits on C5's harness and labels)

**Step 8 — Held-out capture and labels [fill-in, Ari].** Capture with `eval/capture.py` (the pipeline's own fetch, one plain GET per URL; A2.1-D3) *before* labelling and keep the fixture local (gitignored). **Step 9 — The splitter-model rungs.** For each candidate (Step 1 gives the ids; first the next-larger Gemma 4 variant, then one other family if the first fails, so the model is not the only variable), run `--label c6-split-<model> --set gated --runs 5 --splitter-model <id>`; page and status models stay on the parity model, so a change is attributable to the splitter (the A2.1 rule, one variable per rung). Each rung is a results file; the Implementation log has a table of misses per rung by page and show.

**Step 10 — Measure the act-in-title check (D6).** `run_eval` runs no validation, so this needs a small `--rescore`-style helper (in `run_eval.py`) that calls `validation.check_act_in_title` on each stored extraction and its `notes["titles"]` (`C6-PR1-11`). Using the stored extractions from Step 9, count per rung: splitter errors in the labels, and how many produced an `ACT_NOT_IN_TITLE` finding.
