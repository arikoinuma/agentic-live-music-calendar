## Context

### What this milestone is

Dep-D2 makes each metro its own subdomain of an environment's zone (`msp.<domain>`, `msp.staging.<domain>`, `msp.dev.<domain>`). C4 pulls the **minimum** of multi-metro forward: a slug on the metro, resolving the metro from the request host, an apex that sends visitors to the live metro, the non-production gate (Dep-D4) and `noindex`. It does **not** scope queries by metro (`arch-initial.md` §11, "Multi-metro scoping enforcement" stays deferred) and does not attach the production domain (C11, Dep-D11).

The milestone has three halves with different handling, as C3 did:

| Half | Who | What | Verified by |
|---|---|---|---|
| **Code and tests** | Claude (cloud-suited; the host parsing, the gate and the decision order are pure and test-first) | `metro.slug` and its migration, `GET /metro` carrying it, host parsing, `proxy.ts`, the gate, `noindex`, canonical and JSON-LD URLs | `make check`, tests written first |

### What is true today (from C2, C3 and the repo, October 29, 2026)

- **There is no slug, no `proxy.ts`, no canonical URL.** `metro` has `id`, `name`, `timezone` (`app/db/models/calendar.py`); `MetroSummary` is the same three fields; `apps/calendar/` has no `proxy.ts` or `middleware.ts`; `app/layout.tsx` exports `generateMetadata` with a title and description only; `lib/json-ld.ts` omits `url` "on purpose: there is no site URL until the hosted phase".
- **One metro, resolved by being the first row.** `current_metro` (`app/dependencies.py`) returns the lowest-id `metro` row; its docstring says "C4's slug lookup later replaces this function". D9 below decides it does not (the spec keeps scoping deferred).
- **`getAppEnv()` exists** (`lib/app-env.ts`, C3-D7), validated against Vercel's own variables, written so that C4's `proxy.ts` reuses it. It throws when called, never at import.
- **Previews are live** (C3): the Vercel Preview environment holds `API_BASE_URL` and `APP_ENV=staging` for all branches. The `dev` branch does not exist yet, and **dev has no Railway service** (C3-D1: on demand), so there is no dev API for a dev host to read (D10).
- **A custom domain makes a host public.** Vercel's protection covers `*.vercel.app` only (`alpha-deployment-plan.md` §1.1, "Vercel protection"). The moment `msp.staging.<domain>` is added, the app-level gate is the **only** thing between the internet and staging (and the Railway API stays public until C10). So the gate must be built and proven on the `*.vercel.app` URL **before** any domain is attached (an ordering trap, Step 5).
- **No domain is chosen.** Dep-D7: Ari registers at Namecheap and points the nameservers at Vercel when he settles on a name. Everything except Step 6 runs without one.
- **Dev's database is stamped at `67609c405218`, not head** (`environments.md`, C3 Step 3): the new migration's `upgrade` runs the C3 `app_env` migration first when `dev` is next migrated. That is correct but unrehearsed; Step 1's check covers it.

| **D1** | **The gate applies to `dev` and `staging` only.** `prod` is open (it is public at C11; until then Vercel's own protection covers its `*.vercel.app` URL). `local` is not gated (a laptop and the e2e stack are not worth a password). **`noindex` is sent in every environment except `prod`**, `local` included. The environment comes from `getAppEnv()`; if it throws (missing or inconsistent `APP_ENV`), every request answers 503 and says so, because a gate that cannot tell what it guards must not open. | Dep-D4: "non-production environments are gated … and send `noindex`", keyed on `APP_ENV`. | **D2** | **Hosts: one zone per environment, configured; the slug is the one label left after stripping it.** Two server-only variables, set per environment: `SITE_ZONE` (the environment's own zone: `<domain>` in prod, `staging.<domain>`, `dev.<domain>`; **unset until a domain exists**) and `DEFAULT_METRO_SLUG` (optional: **the code default is `msp`**, so the e2e stack, `make dev` and `.env.local` need no new variable; a value that is set but is not a valid slug makes the proxy answer 503, so a typo is visible and never falls back silently; C4-PR1-4). `SITE_ZONE` is **normalised once where it is read** (lowercased, leading dot and trailing dot stripped; C4-PR1-14). A host is classified as exactly one of: **outside** (not in the zone, or no zone configured: `*.vercel.app`, `localhost:3000`, `localhost:3100`) → the default metro, no redirect; **apex** (equals the zone) → redirect to the default metro's host (D5); **metro** (one valid, non-reserved label before the zone) → that slug; **bad** (several labels, an invalid or reserved label) → redirect **straight to the default metro's host**, not via the apex, so a bad host never depends on the apex being attached (C4-PR1-2). Host matching is on a **label boundary**, case-insensitive, port and trailing dot stripped. **A slug is 3–32 characters, `[a-z][a-z0-9-]*[a-z0-9]`** (Dep-D3's codes fit; longer aliases are allowed). The **reserved list is one JSON file**, `apps/calendar/lib/reserved-slugs.json` (`www`, `api`, `admin`, `dev`, `staging`, `app`, `mail`, `ftp`, `status`, plus any Ari adds); the TypeScript parser imports it and a Python test reads the same file and requires that no seeded slug is in it. | Dep-D2 gives the rule; the label boundary is why: `xdev.<domain>` and `msp.evildev.<domain>` must not parse as the dev zone. Outside hosts must work because previews, `localhost` and the e2e stack are all outside every zone (the plan's first test). One JSON file is the smallest thing that keeps two languages in step without generation; the API's deploy root (`apps/api`) cannot read it at run time, which is fine because only a CI test needs to. `dev` and `staging` are reserved because `dev.<domain>` is the dev zone's apex and must never parse as a metro of the production zone. | *Derive the zone from the first label of `Host`:* clever, and wrong for `localhost` and `*.vercel.app`. *Python as the source and TS generated:* the C3.1 pattern, heavier than a list of nine words. |
| **D3** | **`metro.slug` is `String`, `NOT NULL`, unique, with a `CHECK` on the format of D2, added by one migration** that adds the column nullable, backfills `msp` for the one metro (`name = 'Minneapolis/St. Paul'`), then sets `NOT NULL` and adds the unique constraint and the check. A database holding a metro the migration cannot name **fails loudly**, which is the intent. `Metro`, `MetroSummary`, the seed (`METRO_SLUG = "msp"`) and the sample world all carry it. | `GET /metro` carries the slug (spec). It is `NOT NULL` because a metro without one cannot have a host. Expand-contract (`arch-initial.md` §5): the API and worker do not redeploy together, but nothing but the seed and the tests inserts a `metro`, an old API only selects named columns, and the table has one row, so a single migration cannot break a deployed old service. The database owns the format so a hand-inserted `Bad_Slug` is refused whatever the code does. | *Nullable column:* a metro without a host is possible. *Two migrations (expand, then contract):* extra ceremony for one row; revisit if a second metro ever exists first. |
| **D4 ★** | **A slug inside the zone is checked against the live metro only when it is not the default.** The default slug (`msp`) is accepted from configuration with no API call, so the hot path adds no latency. Any other well-formed, non-reserved slug triggers one `GET /metro` from the proxy (short timeout), and is accepted only if it equals the returned `slug`; otherwise redirect to the default metro's host. **If the API cannot answer, fail open**: no redirect, and the request is served as the **default** metro (`x-metro-slug` carries the default slug, not the unverified one, C4-PR1-15), because an outage must not turn into a redirect storm and the page's own fetches will show the outage. The liveness check runs only **after** the gate (`C4-K2`), so it cannot be used by a stranger to probe which metros exist. | Spec: "an unknown slug inside an environment's zone goes to the chooser". The DB is the truth for which metros exist (D3), and the API serves it. With one live metro the extra call fires only for unknown slugs. | *(B) A configured list of slugs per environment* (`METRO_SLUGS`): no API call, no failure mode, but a second copy of what the database knows that must be edited with every metro. *(C) A time-limited in-memory cache:* contradicts the spirit of `B2-D1` (no persistent caching) for a lookup that is rare anyway. **Verified in plan review round 1 (C4-PR1-12):** a `proxy.ts` that imports `server-only` modules (`lib/app-env.ts`, `lib/metro.ts` through `lib/api.ts` and React `cache`) builds and runs on Next 16.4.1; outside a render `cache` simply does not memoise. Step 2 re-checks it once. |
| **D5** | **The apex "chooser" is a redirect, not a page, while one metro is live.** A request to the zone apex (any path and query) redirects 307 to `https://<default slug>.<zone><path>`, and a bad host redirects 307 to the same default host directly (one hop, no dependence on the apex being attached). No `/choose` page and no `/metros` endpoint are built. The page arrives with the second metro, which will also need the list endpoint. | The spec: "redirects to `msp.` while one metro is live". 307 because it is temporary by design. Taking the target from configuration (not the API) keeps the apex working through an API outage. | *Build the page now:* UI and an endpoint with exactly one possible answer. |
| **D6** | **The gate is a shared password, checked by a route handler, remembered in a signed host-only cookie.** `SITE_GATE_PASSWORD` is a server-only secret set per environment (Vercel Preview, scoped by branch like `APP_ENV`, C3-D11); it is not in `Settings` (that is the API's) and is listed in `environments.md`. Unauthenticated requests redirect to `/gate?next=<path>` (non-GET/HEAD requests answer 401 instead). `POST /gate/enter` compares the submitted password to the configured one in **constant time on fixed-length values**: both sides are SHA-256 digested first, then compared with `timingSafeEqual`, because `timingSafeEqual` throws a `RangeError` on buffers of different lengths and a wrong-length guess (or cookie) must be a refusal, not a 500 (C4-PR1-6). On success it sets a cookie named **`__Host-gate`** (`Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, **no `Domain`**, so host-only and the browser itself refuses to widen it, Dep plan §4.2), whose value is an HMAC (key: the password; message: `gate-v1:<APP_ENV>`), `Max-Age` 30 days, then redirects to `next` **only if it is a same-site path**. "Same-site" is decided by **parsing**, not by string prefixes: `new URL(next, "https://gate.invalid")` must have the placeholder's origin, and the redirect uses its `pathname + search` (WHATWG parsing strips tabs and newlines, so `/\t/evil.com` becomes `//evil.com` after any string check has passed, C4-PR1-8). **Both redirects of `POST /gate/enter` (success and wrong password) are 303 See Other**, not `NextResponse.redirect`'s default 307, so the browser does not re-POST the form to a page route or resubmit the password on refresh (C4-PR1-7). Changing the password invalidates every cookie. **If `SITE_GATE_PASSWORD` is unset in a gated environment, the proxy answers 503 (fail closed).** The gate is a courtesy, not security (style guide: the proxy is not an auth boundary; the Railway API is public until C10): no rate limit, no per-user identity, so the password should be long. | Dep-D4 (app-level, any plan). HMAC over a constant makes the cookie unforgeable without the password and needs no session store or second secret. `__Host-` makes host-only a browser-enforced property, which is what keeps the environments from reading each other's cookies. A route handler is a pure request→response function and testable; a Server Action would POST to the page and be reachable around the matcher (style guide, Anti-patterns). | *HTTP basic auth:* no form, but the browser keeps no logout and `msp.staging` and `msp.dev` would each prompt unpredictably. *A cookie containing the password's hash:* a stolen cookie is the hash, which leaks the password's equivalent offline. |
| **D7** | **`noindex` is sent as an `X-Robots-Tag: noindex, nofollow` response header on every response from a non-`prod` environment, including the gate page and redirects, and mirrored in the `robots` metadata.** The 503 "unavailable" response carries it too: an unreadable environment is treated as non-production (C4-PR1-13), and `generateMetadata` catches `getAppEnv()`'s error and emits `noindex` for the same reason (C4-PR1-16). No `robots.txt` with `Disallow: /`. | A header covers non-HTML responses and the gate itself. A `Disallow` would stop crawlers from fetching a page to see its `noindex`, so a URL linked from elsewhere could still be listed bare; with the gate, crawlers see the gate page and its header and nothing else. | *`robots.txt` only:* does not remove an indexed URL and is advisory. |
| **D8** | **Canonical URLs, `metadataBase` and JSON-LD `url` come from configuration, not the `Host` header:** the origin is `https://<resolved slug>.<SITE_ZONE>`; with `SITE_ZONE` unset (the pre-domain state, and Production until C11) there is **no** `metadataBase`, no canonical and no JSON-LD `url`, rather than a wrong one. JSON-LD gains `url` on events and the venue (`lib/json-ld.ts`'s header comment is revised). Non-production environments emit canonicals pointing at themselves (fine: `noindex`). | Spec: "come from the host". Echoing the raw `Host` makes a canonical-injection bug out of any request with a forged header; the host is trusted only after the parser has accepted it against the zone. A `*.vercel.app` alias of production then canonicalises to the real host. **Unverified, checked in Step 2 against `node_modules/next/dist/docs`:** that `alternates.canonical: "./"` resolves per route in this Next version. | *Read `Host` directly:* simple, forgeable. *Hard-code the origin in an env var per environment:* the slug is part of the host, so it would break at the second metro. |
| **D9** | **`current_metro` stays the lowest-id row; the host's slug does not reach the API.** C2-D5's docstring ("C4's slug lookup later replaces this function") is edited to say it did not and why. The slug is used by the frontend for the host check, canonical URLs and (C3.1) `isEnabled(name, { metro })`. | The spec keeps "scoping every query by metro" deferred (`arch-initial.md` §11), and with one metro an in-zone slug other than `msp` redirects (D4), so no request can reach the app asking for another metro's data. Replacing `current_metro` is the second metro's milestone, with the scoping it needs. | *Pass the slug to the API now:* the first half of multi-metro scoping with no second metro to test it on. |

**`C4-K1` — host to metro: strip the environment's zone on a label boundary** (`lib/metro-host.ts`, `parseHost`).
- **Key point of interest:** the environment is the *parent zone*, and the remainder after removing it is the slug (`Dep-D2`, `alpha-deployment-plan.md` §4.2). The match must be on a **label boundary**: `endsWith("." + zone)` or equal to the zone, never a bare `endsWith(zone)`, or `xdev.example.com` parses as the dev zone. What is left must be exactly one valid, non-reserved label; anything else inside the zone is "bad", and anything outside the zone (or with no zone configured) is "outside", left alone.
- **Code (near-exact, for the scaffold's comment):**
  ```ts
  const h = host.toLowerCase().replace(/:\d+$/, "").replace(/\.$/, "");
  zone = zone?.toLowerCase().replace(/^\.|\.$/g, "");   // normalise once; the caller may pass it as typed
  if (!zone) return { kind: "outside" };
  if (h === zone) return { kind: "apex" };
  if (!h.endsWith("." + zone)) return { kind: "outside" };
  const label = h.slice(0, -(zone.length + 1));
  if (!isValidSlug(label) || RESERVED.has(label)) return { kind: "bad" };
  return { kind: "metro", slug: label };
  ```
  (`isValidSlug` and `RESERVED` are written around it; a label containing `.` fails `isValidSlug`, which is what makes `a.b.zone` "bad".)
- **Check:** `pnpm --filter calendar test lib/metro-host.test.ts` (T1). The likeliest mistake: matching `endsWith(zone)` without the dot (the `xdev.example.com` row goes red), or lowercasing the zone but not the host, or stripping the port with a split on `:` that breaks an IPv6 literal (`[::1]:3000` is "outside", a row).

**`C4-K2` — the proxy's decision order: the gate before the liveness check** (`lib/request-plan.ts`, `decideRequest`).
- **Key point of interest:** the *order* of the checks is the design, not any one of them (revised in plan review round 1, C4-PR1-10). (1) An unreadable environment, a malformed default slug, or a gated environment with no password is "unavailable" before anything else (fail closed, D1, D6), and carries `noindex` (C4-PR1-13). (2) Host handling that reveals **nothing from the database** comes next and needs no login: the apex and bad hosts redirect straight to the default metro's host (a pure function of the host string and configuration), which spares a stranger from logging in on a host that was going to redirect anyway. (3) Then the gate, with `/gate` and `/gate/enter` passing without a cookie (or nobody can log in). (4) **Only after the gate** the liveness check of a non-default in-zone slug (D4): that is the one step whose answer depends on the database, so it must not be reachable by a stranger (the redirect-versus-gate difference would tell them which metros exist). It fails open on "unknown", and the default slug is accepted *without* asking. (5) `noindex` is a property of the environment, attached to whatever action results.
- **Code (near-exact):**
  ```ts
  const noindex = !env.ok || env.value !== "prod";
  if (!env.ok || !defaultSlugOk || (gated(env.value) && !input.password)) return { action: "unavailable", noindex: true };
  if (host.kind === "apex" || host.kind === "bad") return { action: "redirect-metro", slug: input.defaultSlug, noindex };
  if (gated(env.value) && !isGatePath(input.path) && !input.cookieValid)
    return { action: input.method === "GET" || input.method === "HEAD" ? "redirect-gate" : "deny", noindex };
  if (host.kind === "metro" && host.slug !== input.defaultSlug) {
    const live = await input.isLiveSlug(host.slug);          // true | false | null (outage)
    if (live === false) return { action: "redirect-metro", slug: input.defaultSlug, noindex };
    return { action: "next", slug: live === true ? host.slug : input.defaultSlug, noindex };
  }
  return { action: "next", slug: input.defaultSlug, noindex };
  ```
  (The `/gate` paths skip step 4's liveness check as well: a request for `/gate` on an unknown slug host is served as the default metro.)
- **Check:** `pnpm --filter calendar test lib/request-plan.test.ts` (T3). The likeliest mistake: running the liveness check before the gate (the "unknown slug without a cookie → the gate, liveness fake not called" row goes red), or calling `isLiveSlug` for the default slug (the "no call" assertion goes red), or treating `isLiveSlug` returning `null` (outage) as "not live" (the fail-open row), or returning `unavailable` without `noindex`.
