## Issues

### PQR1-15: the health routes are the least polished code in the app

**What's wrong (quoted from the source).** "No return-type annotation (`async def health():`); `health_db` returns from
inside `async with`; neither declares a response model." Evidence in the review: `app/main.py:27-50`. Suggested fix:
"`-> dict[str, str]` or a tiny `HealthResponse` model; return after the block; add a module docstring."

**State on `main` today.** PQR1-2 (PR 94) already cleaned the tutorial comments out of `main.py`. What remains of the
finding: `health` and `health_db` have no return annotation, `health_db` returns inside the `async with`, and `main.py`
has no module docstring (the repo's own rule: "every module opens with a docstring", PQR1-6 covers four other modules).

**Fixed means:** both routes are annotated `-> dict[str, str]`, `/health/db` returns after its connection block, and
`app/main.py` opens with a docstring saying what the module is.

### PQR1-17: exception names without an `Error` suffix

**What's wrong (quoted from the source).** "`EmptyResponse` (`nodes.py:66`), `ShowGone` (`calendar_writer.py:73`),
`ScenarioNotRunnable` (N818)." PEP 8: "you should use the suffix 'Error' on your exception names (if the exception actually
is an error)." Suggested fix: "`EmptyPageError`, `ShowGoneError`, and so on."

**What "and so on" covers.** `apps/api/pyproject.toml` carries four per-file `N818` ignores, marked "Remove these lines
when those land": `calendar_writer.py`, `nodes.py`, `sources/embedded_events.py` and
`model_eval/labeled_page_runs/two_run_scenarios.py`. The fourth file holds `_UnknownEncoding`, which the finding does not
name but the lint ignore does. The scope is every class the ignores hide, so all four are renamed and all four ignores
are removed. (The other exception classes in the repo already end in `Error`.)

**Fixed means:** the four classes end in `Error`, every use (code, tests, comments, docstrings) follows, the four `N818`
ignores are gone, and `ruff check` is clean without them.

## Approach

**PQR1-17.** Rename `EmptyResponse` → `EmptyPageError`, `ShowGone` → `ShowGoneError`, `ScenarioNotRunnable` →
`ScenarioNotRunnableError`, `_UnknownEncoding` → `_UnknownEncodingError`, and delete the four per-file `N818` ignores
from `pyproject.toml`. Fails first: delete the ignores before renaming and `ruff check` reports four N818 violations.
The audit string `ShowFailure.error` is `f"{type(err).__name__}: …"` (`calendar_writer.py:113`), so new failure rows read
`ShowGoneError: …`. A test pins that. Nothing in the code or the frontend parses the old prefix (grepped), and rows
already written keep the old class name in their text, which is accurate for when they were written. Historical plan
and implementation docs under `docs/dev/implementations/` and `docs/dev/review/` keep the old names: they record what
was true when they were written, and the review doc is the source of this finding.

**PQR1-15.** Annotate both routes `-> dict[str, str]`, move the `/health/db` return out of the `async with`, add the
module docstring. A small `HealthResponse` model was the review's alternative; it would live in `app/schemas.py` and so
make this T2 (schema change). `dict[str, str]` gets the same typed response in the OpenAPI document with no new model,
and the two routes' bodies are one or two string fields. FastAPI derives the response schema from the annotation, so
`apps/calendar/lib/api-types.ts` changes for the two health operations (generated by `make types`, never hand-edited;
the frontend doesn't call either route). Fails first: a test that reads `app.openapi()` and expects a typed string-map
200 schema for both routes (the `/health` operation currently has none), and two tests that call `/health/db` against
a fake engine, which also pin the behavior the "return after the block" move must keep (the body is returned; a
connection error is not swallowed).
